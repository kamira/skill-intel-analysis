## 動機

`daily-loop` 這個名字把**當時的需求節奏**寫成了**機制的身分**。使用者指出:實際語意是「每次追蹤的循環」,每日只是其中一種節奏。

量測血跡後,有一項對範圍判斷關鍵的事實:**狀態機本身早就是循環制,不是日制**——

| 層 | 現況 | 是否真的綁日曆 |
|----|------|----------------|
| 命名 | `daily-loop.md`、`intel_daily.py`、「每日盤點簡報」 | ✗ 純命名 |
| 資料鍵 | `docs/intel/coverage/YYYY-MM-DD.json`,一日一檔 | ✅ **真的綁** |
| 狀態機 | `intel_daily.py:84` 冷鏈判定讀「最近 3 個 **coverage 檔**」 | ✗ 已是循環制 |
| 紀律 21 | 條文寫「連續 3 個**分析日**」 | ✗ 已是「分析回合」語意 |

也就是說,冷鏈計數數的一直是**回合**;唯一真的把日曆寫死的是 coverage 檔以日期為唯一鍵。這造成一個實際缺陷:**同一天跑兩次追蹤循環會被合併成一個回合**,冷鏈連續計數因此少算——節奏越密,失真越大。

## 使用者故事

1. 作為**非每日節奏的使用者**(每週盤點、或事件驅動盤點),我要這套機制不預設日曆節奏,以便不必為了配合命名而假裝自己每天跑。
2. 作為**一天跑多次的使用者**(危機期間),我要每個循環各自成為一個回合,以便冷鏈連續計數如實反映我實際盤了幾輪。
3. 作為**既有使用者**,我要既有的 `YYYY-MM-DD.json` coverage 檔仍可讀,以便升級不會讓歷史盤點紀錄失效。
4. 作為**維護者**,我要條文與程式用同一個詞(回合/cycle),以便不再出現「文件說每日、程式數檔數」這種語意分岔。

## 決策與取捨

| 決策 | 選項 | 前提假設 | 為何這樣選 |
|------|------|----------|------------|
| `daily-loop` → `tracking-loop` | 保留舊名加註「不限每日」 | 名字是最強的預設值 | 加註不會改變讀者的第一印象;SKILL.md 的 workflow 段本來就叫「追蹤循環 / Tracking loop」,改名是**向既有用語收斂**而非新造 |
| `intel_daily.py` → `intel_loop.py` | 只改文件不改腳本 | 文件與程式須同詞 | 對應故事 4;文件改了腳本沒改,正是本 CHG 要修的那種分岔 |
| 舊腳本名保留一個版本的 shim | 直接刪除 | 使用者可能已寫進自己的排程 | 直接刪會靜默破壞外部呼叫;shim 印棄用警告後轉呼叫新入口 |
| coverage 檔改 `YYYY-MM-DD-NN.json` | 維持一日一檔 | 一天可跑多輪 | 對應故事 2;維持日鍵等於承認「一天只能盤一次」,與本 CHG 前提矛盾 |
| 舊 `YYYY-MM-DD.json` 讀為該日第 01 回合 | 要求使用者手動遷移 | 歷史檔已存在於使用者專案 | 對應故事 3;向後相容成本極低(檔名 regex 加一個可選群組) |
| 紀律 21 條文「分析日」→「盤點回合」 | 不動條文 | 條文是規則正典 | 條文若留「日」,程式數回合就是無依據;改條文才是把語意對齊到既有行為 |
| **不改** `COLD_STREAK = 3` 的數值 | 一併調參 | 3 是既有校準值 | 本 CHG 只改語意單位不改閾值;混改會讓日後回測分不清是哪一項造成的差異 |
